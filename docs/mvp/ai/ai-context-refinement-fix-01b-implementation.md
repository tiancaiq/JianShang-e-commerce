# REFINE-FIX-01B implementation and verification — 2026-09-29

## Status and boundary

**Implemented locally; REFINE-FIX-01B.1 focused live gate GO.** This slice prevents an ordinary, clearly anchored public-search correction from creating a redundant durable permission request, and validates the model's proposed search against the newest executed search. The model still makes the first decision and supplies every search argument. The Agent never constructs or executes a replacement search on its behalf. `REFINE-FIX-01C` generic terminal/SSE recovery, browser acceptance, CTX-02, and rollout are not part of this slice.

The existing `AGENT_MARKETPLACE_V2_*` activation and kill-switch boundary remains. There is no public API or SSE schema change, Product filter change, new storage dependency, migration, or environment-file edit. A new optional private `ToolObservation.refinementRepair` value gives the model a bounded reason for a rejected proposal; it contains no replacement argument or customer data. Older stored observations remain readable.

## Implementation

- `refinement.py` recognizes only short explicit price, condition, RAM, size, wireless, and no-RGB edits when an unexpired `latestSearch` from `REFINE-FIX-01A` exists. A new product request, ambiguous reply, stale snapshot, or explicit pre-search permission request does not enter this path. Query-only attributes remain text in `query`, not Product-verified typed filters.
- The provider prompt, search/confirmation tool descriptions, and discovery Skill distinguish ordinary read-only correction from customer-requested pre-search approval. The first model decision remains `auto`; after a rejected anchored correction, a subsequent decision is constrained to the exposed `search_listings` shape, with arguments still generated by the model. The existing five-decision budget applies.
- `MarketplaceAgentV2ToolPolicy` rejects unrequested `request_confirmation`, wrong read tools for an anchored edit, and search proposals that lose untouched typed filters, retain an old edited value, stack query attributes, or change the product core. Rejections are `CONFIRMATION_INTENT_REQUIRED`, `SEARCH_REFINEMENT_TOOL_REQUIRED`, or `SEARCH_REFINEMENT_MISMATCH`. The optional repair category distinguishes an unchanged filter change, a lost price bound, changed query terms, or an unapplied edit; it does not override validation. A harmless USD value without a price bound is accepted because the current Product search contract does not use currency without a bound.
- The orchestrator withholds early provider text only for a recognized anchored correction. It rejects a premature terminal answer as one in-loop `DIRECT_RESPONSE` observation so a model can recover within the existing budget. This is a narrow 01B guard; it is **not** the general guarded terminal buffering and recovery planned for 01C. No commerce mutation tool is enabled by this path.
- For query-only RAM, size, wireless, and RGB edits, terminal prose cannot assert a verified attribute match. Product's validated cards and zero-result outcome remain authoritative. A successful zero-result search is still the latest executed search and retains its filters for the next correction.

## Verification

Automated tests cover fresh/stale and ambiguous recognition; price supersession; condition, location, category, limit, and price carry-forward; query attribute replacement, word-order and `without RGB` equivalence; new-product reset; explicit and unrequested confirmation; wrong/rejected model proposals; bounded recovery; no leaked permission text; and no false verified attribute claim. Final local results: **422 V2 tests run (3 skipped, 0 failures)**; **1,063 full Agent tests run (47 skipped, 0 failures)**; **12 real-MySQL persistence tests run (0 failures)** after the final optional repair-hint addition.

An isolated Agent process at `127.0.0.1:18086` used this worktree with the existing local MySQL, Keycloak/Auth, Product, and live provider. The shared Agent container on 8086 and frontend were untouched. The disposable buyer-only fixture accounts were disabled after every run. The local acceptance harness inspected only allowlisted persisted Agent search-action fields, not credentials or raw provider output.

Live runs repeatedly completed the core laptop → under $1000 → 16GB RAM chain, $1000 → $1500 correction, NEW laptop → under $1000, 16GB → 32GB query replacement, and new-product reset with one executed search per clear correction and no durable permission. An explicit “ask me before searching” still produced `CONFIRM_ACTION`. In run `mulr1qy6`, keyboard → wireless → under $100 → no RGB completed all four searches; the final executed query was `keyboard wireless no RGB` with `maximumPrice=100` and no verified RGB filter claim. Product returned `CATEGORY_UNAVAILABLE` for that exact query, which is not an Agent failure or inventory claim.

The monitor → 27 inch → under $300 → 32 inch chain is **not reliably accepted**. Synthetic-only diagnostics showed the live model sometimes dropped `27 inch` while adding the price, or dropped the executed `maximumPrice=300` while replacing 27 with 32 inch. Policy correctly rejected those calls; the model sometimes repeated an invalid proposal until the five-step budget ended. The bounded repair hints and prompt examples were added after observing that failure, but the final monitor-only run `mulrcu6d` stopped on an earlier model-response failure and did not demonstrate an end-to-end success. Do not treat a completed HTTP/SSE turn or a persisted old snapshot as a successful refinement search. The final implementation needs repeated same-build live passes and authenticated browser verification before CTX-01-RC or V2 rollout can be marked GO. The remaining guarded terminal/stream failure path is tracked separately in `REFINE-FIX-01C`; do not weaken policy carry-forward to hide it.

### REFINE-FIX-01B.1 — structured query-attribute repair (2026-09-30)

The preceding Flow B was **0/5**, with four `SEARCH_REFINEMENT_MISMATCH` rejections per failed `27 inch.` turn (20 total) and no second-turn search. The prior optional repair value identified only a mismatch category. Although `latestSearch` separately contained the executed `monitor` query and `$300` maximum, the recovery decision lacked one explicit, bounded statement connecting that state to the customer's query-attribute addition. The precise rejected proposal arguments from the original run were not retained, so the evidence supports this feedback gap, not a claim that every proposal dropped price in the same way.

`ToolObservation.refinementRepair` now accepts a typed `SEARCH_REFINEMENT_REPAIR` signal with `mismatch`, a compact `currentSearch` projection of executed supported constraints, `requestedEdit` (`field`, `operation`, `value`), and preservation/application requirements. Flow B describes `query=monitor`, `maximumPrice=300`, `currency=USD`, and `QUERY_ATTRIBUTE/ADD/27 inch`. The existing four mismatch categories and validation rules remain unchanged. After a mismatch, the next in-loop decision is exposed only to `search_listings`; its tool choice is constrained to that read, but the model must still author every argument. No backend replacement search, extra decision loop, mutation tool, public schema, Product filter, migration, or environment change was added. Legacy string-valued repair observations remain readable. A safe mismatch category is logged without the rejected arguments or private provider material.

Deterministic coverage includes the A/B/C asymmetry, laptop RAM, keyboard wireless/no-RGB, condition and city preservation, wrong-product and missing-edit rejection, structured-observation safety, legacy repair compatibility, first-bad/second-good execution (exactly one search), repeated-bad five-decision exhaustion (zero searches), ambiguity, new-product reset, and explicit confirmation. The full Agent suite ran **1,067 tests, 47 skipped, 0 failed (1,020 passed)**; the real-MySQL persistence integration ran **12 tests, 0 skipped, 0 failed**. The full suite includes the ContextBuilder, provider, Skill, policy, orchestrator, V2 service, SSE/contract, CTX-00, and CTX-01 regression tests.
