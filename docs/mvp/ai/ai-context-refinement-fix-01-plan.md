This follows [CTX-01-RC](ai-context-ctx-01-runtime-acceptance.md). The earlier context-only gate was NO-GO; the bare-query follow-up has [focused 01E verification](ai-context-refinement-fix-01e-implementation.md), not final release approval. The explicit-query-replacement follow-up is recorded in [01D implementation and verification](ai-context-refinement-fix-01d-implementation.md). It is not CTX-02 and does not authorize rollout. ## 1. Executive summary and classification

The live failure is **not a malformed Responses API decision**. In reproduced price, condition, and RAM follow-ups, `gpt-5-mini` returned a completed, valid *single assistant text decision* (one `message` plus one `reasoning` output item). The provider accepted it. The orchestrator then rejected the text as `MODEL_RESPONSE_UNSUPPORTED` because it promised results without a current search/card, requested yes/no with no pending confirmation, asked too many questions, or exposed an internal condition enum. On these no-search turns, the current guarded fallback cannot safely synthesize a new search; it fails the invocation after SSE may already have emitted text.

At investigation time, the model could choose that prose because ordinary numeric/attribute refinements were not represented by the existing exact Product-facet `contextualRefinement`; the latest search observation preserved only filter *categories*, not applied filter *values*; the tool choice remained `auto`; and no narrow terminal requirement rejected a redundant permission question when there was no pending interaction. The discovery Skill was available but loading it was optional and per-turn. A tool description also calls `request_confirmation` a control for a “materially changed refined search,” while policy currently requires only a referenced listing for that proposal. This wording and permissive gate can encourage unnecessary consent behavior; the live failures observed prose requests, not a `request_confirmation` tool call.

Classification: **Outcome D — multiple pre-existing refinement/planner and terminal-handling causes**, not an evidenced CTX-01 regression and not a provider/parser defect. CTX-01 attribution is strongly disfavored by live shadow parity with the pre-CTX-01 model-visible construction (see §5), but there was no separate byte-identical full pre-CTX runtime. Keep CTX-01-RC **NO-GO** until the scoped fixes and acceptance gates pass.

## 3. Exact `MODEL_RESPONSE_UNSUPPORTED` path

`OpenAIMarketplaceAgentV2Model.decide` in `provider.py` (roughly lines 195–355) sends a Responses request with `store=False`, `truncation="disabled"`, and `max_tool_calls=1` when tools are supplied. The decision's `tool_choice` is computed by `_required_tool_choice`; ordinary refinement reaches `"auto"`. The stream accepts completed text or one function call, ignores `reasoning` and other non-function output items for decision selection, parses function arguments as JSON, and requires exactly one of text, Skill selection, or tool proposal. A malformed argument, mismatched streamed/final text, zero actions, or mixed/multiple actions raises `ValueError`, which the orchestrator maps to **`MODEL_DECISION_INVALID`**, not this incident's code. Incomplete/provider failures have separate classifications. Official OpenAI documentation confirms that Responses outputs are typed items, so a `reasoning` item alongside one `message` or one `function_call` is not itself an invalid multi-decision shape: [Responses items](https://developers.openai.com/api/docs/guides/migrate-to-responses), [function calling](https://developers.openai.com/api/docs/guides/function-calling).

The current code can create `MODEL_RESPONSE_UNSUPPORTED` from (a) `_CustomerTextStream._drain` blocked action phrases, (b) `_grounded_recommendation_content` when no supported recommendation/ordinal comparison can be formed, or (c) `_validate_terminal_response` (roughly lines 3060–3330). The latter rejects these classes: missing required owned-order/return read; private/internal cart metadata, enums or field names; excessive/refinement questions or yes/no without pending state; false action/ID/ordinal/count claims; result presentation without current cards; cart or order claims without authoritative observations; repeated confirmed-search prompt; and unsupported comparison assertions or ordering. A test fake may also raise a provider failure with this kind, but the real provider's current parser does not generate it for the observed output shapes.

The safe probe logged these **exact reproduced origins** in `_validate_terminal_response`:

| Source line | Rejected condition | Live interpretation |
| --- | --- | --- |
| `orchestrator.py:3208` | Result-presentation claim with no current attachments or commerce grounding | Model talked as though a new result set had been shown, but did not search. One post-search occurrence was replaced by the existing grounded fallback and completed; pre-search follow-ups cannot use that fallback. |
| `orchestrator.py:3123` | `yes/no` in prose with no `WAITING` interaction | Model asked for search permission without a durable confirmation. This caused failed price/RAM/correction turns. |
| `orchestrator.py:3117` | More than one question or a `Refine:` line | Model returned a questionnaire instead of executing the refinement. |
| `orchestrator.py:3104` | Internal condition enum or other internal count/field text | Model leaked an internal representation in a condition refinement; the validator correctly rejected it. |

Each of these probe events followed a completed provider response with `item_types={"message":1,"reasoning":1}`, `has_text=true`, no function call, and `tool_choice="auto"`. Normal searches showed `{"function_call":1,"reasoning":1}` and one `search_listings` proposal (or a permitted `load_skill` first), followed by a separate terminal message decision. No observed failure involved malformed JSON, simultaneous text and tool, multiple tool calls, or an unsupported output item. The `MODEL_PROVIDER_UNAVAILABLE` variant is distinct. The public SSE code maps these failed invocations to `MARKETPLACE_AGENT_V2_STREAM_INTERRUPTED`; `stream_provider_text` can be true before validation, explaining `message_started → text_delta → error`.

## 4. Orchestrator, Skill, and search-tool analysis

The five-step loop in `orchestrator.py` (about lines 1133–1966) constructs a fresh packet each decision, offers enabled schemas, accepts one direct response or one proposal, validates proposals through `MarketplaceAgentV2ToolPolicy`, appends rejections/observations, and forbids a second search in one invocation. A successful search removes all tool schemas for the next synthesis decision; policy separately rejects duplicate calls. Skill selection consumes a decision; `marketplace-discovery` then narrows schemas to `check_availability`, `search_listings`, and `get_listing`. In the failed follow-up decisions, no Skill had been loaded, `search_listings` was available, and the model nevertheless returned text. This is not Skill narrowing or duplicate protection blocking the search.

`_contextual_refinement_selection` (about lines 2336–2390) recognizes only a short reply exactly matching the latest Product-owned `SUBTYPE` facet or revalidated `CATEGORY`. That internal `contextualRefinement` makes prose rejectable and grounds an exact search query. Price, RAM, condition, and their corrections all showed `contextual_refinement=false` in the probe. The ordinary `_terminal_tool_requirement` does not require a read-only search for these follow-ups. Their scope classifications were typically `CONTEXTUAL_MARKETPLACE_FOLLOW_UP` or `SHORT_PRODUCT_PHRASE`, not high-confidence explicit discovery. `_results_first_failure_decision` applies only to a simple, unfiltered, high-confidence explicit discovery, so it correctly does not synthesize a filtered search from an ambiguous short phrase. `_required_tool_choice` then stays `auto` and the provider may return prose.

The provider system prompt says terse refinements should compose with the active product, and `marketplace-discovery/SKILL.md` says resolve from the conversation and search. Neither supplies an exact applied-price snapshot or a per-turn rule forbidding a permission question for an unambiguous read-only refinement. The `request_confirmation` tool description's “materially changed refined search” language is broader than the provider's explicit “ask me/confirm with me before search” rule; policy currently checks a referenced listing but not explicit pre-search permission. Ordinary discovery does not require approval. It must continue to support deliberate customer-requested approval, and any proposed tightening must retain that path.

`SearchListingsArguments` and `DiscoverySearchRequest` support query, category, condition, min/max price plus currency, city/county, and limit. The Product adapter forwards those fields and revalidates returned listings. They do **not** expose a typed RAM-minimum filter. RAM can currently enter only the free-text `query`; that cannot justify a claim that every shown listing meets a verified 16GB or 32GB attribute minimum. Product owns that truth and any future typed attribute-search contract. At the investigation baseline, `ToolObservation` persisted `normalizedQuery` plus `filterCategories` (for example `MAXIMUM_PRICE`) but **not the applied numeric value**. `agent_tool_calls` stored an argument hash, not reconstructible arguments. Recent user messages could contain `$1000`, but the canonical executed filter was not explicitly available to the next model decision. A correction to `$1500` therefore relied on conversation interpretation rather than a typed last-search snapshot.

## 5. Strongest practical equivalent pre/post comparison and CTX-01 attribution

The earlier Docker control differed in source files, so it is directional evidence only. For this investigation, the isolated **same-build** probe reconstructed the pre-CTX-01 `AgentContext` expression from the old orchestrator diff for every live decision, while the actual request used `MarketplaceContextPacket.to_agent_context()`. It compared complete camel-case JSON objects (including recent messages, ordered references, last-five customer-safe observations, pending/workflow, contextual refinement, scope, and Skill state) and logged only equality. It also compared the selected turn dialogue/cards/observations to the moved legacy helper logic. Every emitted `turn_parity` and `legacy_model_context_equal` was `true`, including failing follow-ups and post-search synthesis. Tool names/order were generated by the same registry; source diff shows CTX-01 changed the construction site, not provider/system prompt or schema order. The probe logged no CTX-01 trace fields sent to the provider.

This is stronger **model-visible input parity for observed turns** than the non-identical old container, but it is not a separate stochastic pre-CTX provider run. It cannot exclude an unobserved CTX-01 edge case. For the reproduced failure, however, the same effective input would have reached the pre-CTX-01 model path, and no differing CTX-01 projection explains a valid but wrong text decision. Do not change ContextBuilder to fix this incident without a failing parity fixture.

## 6. Proposed narrow implementation slices

### REFINE-FIX-01A — Canonical current-search snapshot (implemented locally)

Persist only the latest successfully executed **search** arguments in the existing Agent-owned observation/action JSON: normalized query, typed applied price/currency/condition/location/category, observed-at/expiry, and a bounded indicator of whether the result set was actually displayed. Project a customer-safe subset beside the latest search observation for the next turn. Do not create a general active-goal store, new MySQL column, public API field, or cross-session memory. A new explicit product search replaces this snapshot; stale/unavailable observations do not authorize claims about current inventory. Keep prior cards separate from authoritative fresh Product results. Characterize first whether the existing `normalizedQuery` can safely serve as the query base for replacing a RAM term; if not, add one narrow search-concept field to the internal tool/observation contract with explicit tests. Do not infer missing RAM facts from titles.

Expected files: `marketplace_agent_v2/schemas.py`, `tools.py`, `context_builder.py` or its strictly scoped projection, `service.py` only if observation restoration needs it; corresponding provider/ContextBuilder/persistence tests. No migration. This intentionally changes the internal model-visible shape, unlike CTX-01; update the approved internal contract and parity fixtures at implementation time.

Implemented internal contract: a successful `search_listings` observation now contains optional `appliedSearch` with the executed canonical query, Product-supported typed category/condition/price/currency/location filters, limit, five-minute observed/expiry window, and `resultsDisplayed`. The latter means at least one result from that search was included as a validated attachment in the completed assistant message; the server cannot attest to browser rendering. The action JSON stores it without a new table/column; a failed executed search whose assistant turn completes stores a safe failure observation that supersedes an older snapshot. ContextBuilder selects the newest search across the bounded 100-message actor/session window, independent of the last-12 observation list, and projects a single unexpired `latestSearch` in the private provider DTO. It omits that prior snapshot after a current search and omits duplicate applied filters from ordinary model-facing observations. Older action JSON without `appliedSearch` remains readable and yields no snapshot. `ctx-01-v2` identifies the deliberate internal projection change; no public API or SSE field changed.

`SearchListingsArguments` already removes price prose only when it exactly equals the typed price bound. Thus the executed query can retain `16GB RAM` as free text, but a conflicting price phrase may remain. 01A records what actually ran; it does **not** rewrite a later `$1000 → $1500` or `16GB → 32GB` proposal, enforce carry-forward, or prevent a permission loop. Those decisions and validation belong to 01B/01C. No separate product-concept field was added because the current executed query remains the exact input needed to characterize those cases without guessing a new concept. The snapshot never proves current inventory or a typed RAM attribute.

01A verification: 408 V2 tests passed (three environment skips), 1049 full Agent tests passed (47 environment skips), and 12 real MySQL persistence tests passed, including an action-JSON snapshot round trip and actor isolation. Unit tests cover success/failure, typed filters, provider projection, latest-search supersession, the independent observation cap, legacy action compatibility, expiry, and completed-message display marking. This was not a live-provider/browser acceptance run; the known refinement failure remains open.

Focused live-provider and persistence acceptance is now recorded in [REFINE-FIX-01A acceptance](ai-context-refinement-fix-01a-runtime-acceptance.md). The narrow snapshot state contract is GO; the 01B/01C behavior and broader CTX-01-RC release gate remain open.

### REFINE-FIX-01B — No redundant read-only permission, with model-first validation

Implemented locally on 2026-09-29; the narrow 01B.1 structured repair passed focused A/B/C acceptance 5/5 each on 2026-09-30. See [01B implementation and verification](ai-context-refinement-fix-01b-implementation.md). REFINE-FIX-01B is GO for its focused gate, while CTX-01-RC browser/rollout sign-off remains NO-GO. This status does not move 01C into this slice.

Clarify `marketplace-discovery/SKILL.md`, the provider's refinement instructions, and the `search_listings`/`request_confirmation` descriptions: a customer-stated, understandable price/condition/query-attribute correction advances the active search without permission; `request_confirmation` is available only for an **explicit customer request** to ask before searching. Add policy validation for that explicit intent, preserving the existing durable single-use flow. In the orchestrator, let the model make the first decision; if it returns search-permission prose for a clearly anchored read-only refinement, reject that terminal decision with one safe structured observation inside the existing five-step loop. Do **not** use a broad regex intent router or silently construct tool arguments. Any recognition must be bounded to an already Product-grounded current search plus a narrow, customer-explicit constraint edit; genuinely ambiguous replies such as “make it better” may still clarify. The model must propose `search_listings`; policy validates one query and the carry-forward/supersession of supported typed filters against the snapshot. No automatic commerce mutation, no second search in the same turn.

Expected files: `provider.py` prompt/tool-choice wording, `skills/marketplace-discovery/SKILL.md`, `tools.py` schema descriptions/observation, `policy.py`, `orchestrator.py`, and focused tests. The implementation must explicitly decide how to represent RAM as **query text only** and make no verified RAM-filter claim until Product supports it.

### REFINE-FIX-01C — Guarded terminal recovery and SSE discipline

Implemented locally on 2026-09-30. Two fresh-session live passes of each of four refinement/correction flows passed the focused 01C gate; see [01C implementation and verification](ai-context-refinement-fix-01c-implementation.md). The authenticated browser and CTX-01-RC rollout gates remain open.

For a current-search-dependent refinement, do not publish model text until terminal grounding/presentation validation succeeds. Today `stream_provider_text` may emit an invalid permission/result claim before `_validate_terminal_response` raises, yielding `text_delta → error`. After buffering, a rejected **valid text** decision may create at most one category-specific `DIRECT_RESPONSE/REJECTED` observation and consume the next of the existing five model decisions. The model can then propose a read-only search with policy-checked arguments or one focused clarification. Do not call the provider outside the loop, do not replay an uncertain write, and do not run a duplicate search; if there is no safe supported continuation or the budget is exhausted, return the existing guarded failure/fallback. Preserve fast streaming for unrelated direct answers. Keep the validator's privacy/internal-enum refusals authoritative; never pass its rejected text through to SSE or persistence.

Expected files: `orchestrator.py` streaming/terminal branch and observation reason, `provider.py` only if the existing recovery tool choice needs a narrow signal, `schemas.py` for the safe reason enum, SSE/service tests. Treat 01C as independently reviewable from 01A/01B. **Do not add a generic provider-parser retry**: the reproduced provider decisions were valid, and blindly repeating an API call would be non-deterministic, costly, and potentially unsafe. Any one-decision corrective attempt must count toward five and happen before any action or text is committed.

## 7. Alternatives, safety, and risks

- **CTX-01 rollback/parity edit:** unsupported by the live equality evidence; risks disturbing passed >100-message, actor-isolation, and reference behavior.
- **Prompt-only tweak:** useful but insufficient as a reliability gate; the current prompt already asks the model to compose “under 200” with the active product, yet live refinements failed.
- **Force `tool_choice=search_listings` on every short message:** violates model-first behavior, misroutes ambiguous questions/comparisons, and bypasses useful clarification. The proposal retains a first model choice and narrows only after a validated, anchored refinement rejection.
- **Blind Responses retry or generic output-shape repair:** not justified by this evidence. The official response shape was valid; a retry could duplicate future consequential actions or exceed the budget.
- **Treat RAM as a Product filter now:** unsupported by the current Agent→Product search DTO. Keep it as explicit query text and disclose that result attributes are not verified; add a separate approved Product search decision if exact RAM filtering is required.
- **New Redis, goal memory, or schema:** unnecessary for this current-search problem and expressly deferred.

Risks to control during implementation: stale prior search state, false carry-forward after a new product request, replacing the wrong numeric constraint, treating one previous card as a new result set, accidental confirmation creation, prompt/tool schema drift, extra model cost, and buffering latency. The owning Product API must continue to revalidate every shown card; policy must remain authoritative for authorization and duplicates.

## 8. Test and live acceptance plan

Add deterministic tests *before or alongside* each implementation slice:

1. Provider/parser: normal assistant; one valid call; malformed arguments; multiple calls; text plus call; unknown extra item; unsupported-only item; completed versus incomplete; and any approved bounded correction. Assert exact `MODEL_DECISION_INVALID` versus `MODEL_RESPONSE_UNSUPPORTED` mapping, `store=False`, `truncation="disabled"`, `max_tool_calls=1`, no private output logging, and no sixth decision.
2. Context/search snapshot: latest search only; filter values and observed time survive persistence/reload; price `$1000 → $1500` supersedes rather than coexists; condition `NEW` carries into under-$1000; query `16GB → 32GB` replaces rather than appends; new product and expired/failed search invalidate appropriately. Assert CTX-01 packet equality for unchanged fields and deliberate additive projection only.
3. Refinement flows: `laptop → <$1000 → >=16GB`, `laptop → <$1000 → <$1500`, `keyboard → wireless → <$100 → no RGB`, and `monitor → 27 inch → <$300 → 32 inch`. Assert one search per turn when unambiguous, correct supported Product filter values, no duplicate/permission loop, and no false RAM verification. `Make it better` must still permit focused clarification. A user-explicit “ask me before searching” must still prepare exactly one durable confirmation; plain `$1000` must not.
4. Failure and SSE: rejected invalid text never emits `text_delta`; one bounded rejection consumes a model step; successful correction emits one accepted USER, one final ASSISTANT, truthful tool activity/cards, and `done`; failed correction emits only guarded error/partial history. Stop, response-only Retry, duplicate-policy, Skill narrowing, actor/session isolation, and post-search fallback remain green. No mutation tool may be executed in a refinement test.
5. Run the V2-focused suite, full agent-service suite, MySQL integration, contract/SSE tests, and production build as proportionate to touched files. Current investigation baseline: **401 V2 tests run, 3 skipped, 0 failures**; no production code was changed during this run.

Then run at least two repeated live passes of each original three-turn and correction sequence with fresh sessions against the same isolated CTX build and Product data, plus a truly equivalent pre-CTX build if the model-visible parity test ever fails. Record safe decision/output-item types, selected Skill, tool name, applied filter categories/values (not private raw arguments), validated/card counts, terminal SSE, and persisted exact-once history. Recheck an authenticated browser flow and refresh before revisiting CTX-01-RC sign-off. Do not auto-retry an uncertain live turn. The results-first Skill also requires Product-revalidated top-K relevance, but unrelated accessory/retrieval quality should have its own owner and gate.

## 9. Rollback, deferred work, and release recommendation

Implement each slice behind the existing V2 capability/kill switch and review it separately. If a new internal search snapshot or recovery guard regresses direct answers, explicit confirmations, or Tool policy, revert that slice's internal code and keep the existing guarded failure behavior; no data migration should need rollback. An additive observation field must be optional when reading older rows, and rollback must ignore it safely. Do not change the public V2 API/SSE names, Product ownership, provider storage/truncation, or commercial authorization.

The evidence currently supports working on a pre-existing Agent refinement/terminal path, not on CTX-01 projection.
