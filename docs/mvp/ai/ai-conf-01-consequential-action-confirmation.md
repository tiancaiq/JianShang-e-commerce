# AI-CONF-01 Consequential Action Confirmation

Status: implemented as a confirmation foundation and reused by the separately
gated AI-CHK-01 whole-cart submit capability.

## Problem

The original Marketplace Agent V2 `request_confirmation` control stored a
single `RUN_REFINED_SEARCH` interaction in `agent_sessions.preference_state_json`.
It was actor/session-bound and single-use under a row lock, but it had no
originating invocation, expiry, resource-version, financial-fact, or dedicated
action identity. Those limits were acceptable for a reversible search, not for
a future checkout, order cancellation, return, or other Level 3 action.

AI-CONF-01 makes the backend confirmation record authoritative. Session JSON
remains a display and conversation-recovery projection only.

## Contract

`agent_confirmations` stores:

- confirmation, actor, and Marketplace Agent V2 session IDs;
- the invocation that prepared the action and an optional workflow ID;
- exact capability, capability version, and action name;
- canonical immutable arguments and their action fingerprint;
- optional target resource IDs with real owner-provided version or snapshot
  tokens;
- optional named amount/currency facts;
- a human-readable summary derived from the typed stored action;
- risk level, creation time, and backend expiry;
- a stable dedicated action key;
- lifecycle state and confirmation/consumption/cancellation/invalidation
  metadata;
- a safe result category when a future executor records one.

Risk Level 3 or higher requires `expires_at`. Target and financial fields are
optional for current refined-search confirmation because that workflow has no
versioned resource or money fact. Future workflows must populate them from the
owning service rather than inventing values in Agent Service.

The canonical fingerprint covers contract version, capability, capability
version, action, normalized arguments, sorted targets, target versions or
snapshot fingerprints, and sorted financial facts. Canonical JSON comparison is
structural and key-order independent; prompt text and arbitrary JSON string
comparison are not used.

## State machine

```text
prepare -> PENDING
PENDING -> CONFIRMED | CANCELLED | EXPIRED | INVALIDATED
CONFIRMED -> CONSUMED | CANCELLED | EXPIRED | INVALIDATED
CONSUMED | CANCELLED | EXPIRED | INVALIDATED -> terminal
```

`CONFIRMED` records explicit approval but is not execution authority by itself.
`CONSUMED` means one exact action claim won the atomic database transition.
Terminal rows cannot be revived.

One generated active marker permits at most one `PENDING` or `CONFIRMED` row
per actor/session. Preparing a genuinely new action invalidates the previous
active row as `SUPERSEDED`. One originating invocation may prepare only one
immutable fingerprint. Response retry therefore returns the existing
confirmation and action key; it cannot silently generate a new identity.

## Ownership and workflow binding

The confirmation row has foreign keys to the owned Agent session and originating
invocation. Every read or transition predicates confirmation ID, authenticated
actor ID, and session ID. Confirmation and consuming invocation lookups also
require that same actor/session. No model schema contains an actor, owner, or
action key field.

A confirmation from one conversation is never searched globally by actor and
cannot authorize another conversation. A wrong-actor or wrong-session lookup is
non-revealing `NOT_FOUND`.

## Exact action claim

A future caller must present the same capability, capability version, action,
typed arguments, targets, and financial facts that were stored. Mismatch
invalidates the row and returns a bounded reason. If a stored target has a real
version token, the current owner-supplied version must still match before the
atomic claim. Current policy and authorization booleans are also required;
denial invalidates the confirmation.

Confirmation never replaces domain revalidation. The required future order is:

```text
load stored action
-> current capability policy
-> current actor authorization
-> current owning-service resource/version validation
-> atomic CONFIRMED-to-CONSUMED claim
-> domain command with the stored action key
```

Agent Service does not become the price, checkout, payment, order, or refund
authority.

## Expiry and action identity

`AGENT_MARKETPLACE_V2_CONFIRMATION_TTL_SECONDS` configures the backend TTL from
60 through 3,600 seconds and defaults to 900 seconds. The configured TTL is
applied to newly prepared refined-search confirmations and is the default for
future consequential preparation. Tests inject explicit clocks.

The action key is `agent-action-{confirmationId}`. It is generated by the
application, never by the model, unique in MySQL, stable for retry/reconnect,
and distinct for a new originating invocation. A future owning service must use
this stable identity as its idempotency key or map it through a documented
adapter. A replay never receives a fresh key.

## Existing integrations

`request_confirmation` remains the only provider-visible confirmation tool and
still prepares only `RUN_REFINED_SEARCH`. The tool creates a typed provisional
interaction; the service persists the durable confirmation and session display
projection in one transaction before the next model decision may display a
question. The displayed question uses the stored deterministic summary.

On `Yes`, `Confirm`, `Go ahead`, or `Do it`, the backend resolves the exact
actor/session row, records `CONFIRMED`, and atomically claims `CONSUMED`. Search
arguments are reconstructed from the durable record. A second or concurrent
confirmation cannot execute again. `No`, `Never mind`, `Don't do it`, or
`Cancel that` moves the row to `CANCELLED`. Ambiguous text such as `maybe` is
not consent.

Pre-V21 session-only confirmations have no durable origin/fingerprint and fail
closed as `INVALIDATED`; the customer must prepare a new search confirmation.

Ordinary cart mutations remain Risk Level 2 and confirmation-free under
AI-COM-01.

AI-CHK-01 adds the first Level 3 use: `SUBMIT_CHECKOUT`. Its durable row binds
the exact actor/session/origin, checkout and cart fingerprints, cart version,
total, currency, expiry, and stable action key. Current Order checkout/cart and
Inventory reservation facts are revalidated before one `CONSUMED` claim. The
application, not the model, then invokes the exact stored checkout through the
normal mock Payment and Order workflow. Checkout binding arguments remain
server-side while the browser receives only the safe summary and lifecycle.

## Refresh, reconnect, retry, and failure

The confirmation row and display projection are MySQL durable. Browser refresh,
SSE reconnect, or Agent restart reads the same state and never confirms,
consumes, or duplicates it. The originating invocation uniqueness constraint
stabilizes Retry. If an originating response fails after preparation, the
confirmation is invalidated so an unseen or partial question cannot leave
hidden authority behind.

Storage errors fail closed. No failure branch falls through to tool execution.

## Safety and policy invalidation

AI-POL-00 Level 5 handling invalidates a waiting or confirmed action before
model or tool work. A later `Yes` cannot revive it. A current capability kill
switch, policy denial, authorization loss, action mismatch, changed financial
fact, or stale resource version also prevents consumption and invalidates the
row. Confirmation does not freeze permission or policy state.

## Audit and privacy

`agent_confirmation_transitions` records safe lifecycle metadata: actor,
session, confirmation, originating or transition invocation, from/to states,
timestamp, correlation ID, reason, policy result, and result category. The
confirmation row stores only bounded normalized bindings needed to identify and
revalidate the action.

Private reasoning, prompts, bearer credentials, card data, secrets, addresses,
raw downstream payloads, and unrestricted user content are never stored in the
confirmation tables. Provider context receives only the display-safe summary,
action label, and lifecycle—not IDs, arguments, expiry, target versions,
fingerprints, or action keys.

## Migration

Forward-only Agent Flyway V21 creates `agent_confirmations` and
`agent_confirmation_transitions`, active-row and action-key uniqueness,
actor/session/origin foreign keys, lifecycle checks, and actor/session, expiry,
and fingerprint indexes. Existing migrations are unchanged.

## Verification boundary

The production registry still exposes no checkout, payment, place-order,
cancel-order, return, refund, seller mutation, admin, HTTP, SQL, shell, or
filesystem tool. A test-only contract and MySQL harness exercise financial,
resource-version, policy, expiry, cancellation, actor-isolation, retry, and
concurrent-consume behavior without registering a fake production tool.

Verification on 2026-09-02 completed:

- 884 Agent Service tests passed with 45 environment-gated skips;
- all three disposable MySQL 8.4 confirmation integration tests passed,
  including the concurrent consume race;
- all 23 focused Angular Agent tests passed;
- the Agent-enabled Angular production build passed;
- Flyway applied V21 to the local MySQL 8.4 stack and validated all 21 Agent
  migrations;
- Python compilation, diff whitespace checking, and the changed-file secret
  scan passed.

The deployed Agent and frontend images were healthy after V21. Live browser
confirmation scenarios remain a release follow-up because the only connected

Automated persistence, service, SSE/history, and real-MySQL tests cover the
refresh, retry, terminal-state, and single-use backend contracts in the
meantime.
